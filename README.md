# 宇宙航行全景 · 2026 年 9 月

一个十板块的静态站点：从一枚已经复用 37 次的猎鹰 9，一直问到光速飞船、冬眠舱和星际通信，
最后把前九个板块的条件收拢成一版星船总体设计。

每个板块都尽量把三件事分开写清：**已经做到的**、**正在验证的**、**还只在纸上的**。

## 重新生成

```bash
python3 tools/build.py            # 生成 assets/space*.svg + index.html + sections/*.html
python3 tools/check_designs.py    # 九张设计图自检（文字越界 / 重叠）
python3 tools/modelrigs.py        # 十一个可旋转模型的自检（渲染包围盒 / 编号点 / 路线图分组）
python3 tools/check_figs.py       # 51 张配图自检（46 张技术路线 + 5 张板块十，同上两类问题）
python3 tools/export_figures.py   # 导出 figures/*.svg（改了 designs.py 的图之后要重跑）

# 页面级校验需要 playwright（先把站点起在本地：python3 -m http.server 4321 --bind 127.0.0.1）
NODE_PATH=<node-workspace>/node_modules node tools/check_site.js   http://127.0.0.1:4321/
NODE_PATH=<node-workspace>/node_modules node tools/check_visual.js http://127.0.0.1:4321/
```

- `check_site.js`：11 个页面的结构校验——横向溢出、侧栏/顶部导航切换、移动端表格转卡片、
  页内锚点、跨页链接 HTTP 200、控制台错误与资源加载失败。
- `check_visual.js`：视觉专项校验——关键文字在深色面上的**对比度**（按 WCAG AA 阈值）、
  舷窗背景图是否真的加载、进场动效有没有把内容留在不可见状态、首屏数字动画有没有卡在 0。

注意：页面里每张图的右下角有一个「打开矢量原图（SVG）」链接，指向 `../figures/NN-slug.svg`。
**改了 `designs.py` 里的图之后必须重跑 `export_figures.py`**，否则页面上的图和下载到的原图会不一致。

站点是「内容即数据」结构：板块内容写在 `tools/content_a.py` / `content_b.py` / `content_c.py`，
技术链路写在 `tools/chains.py`（每一环的详解与创业视角在 `tools/chainbiz.py`），
成本写在 `tools/costs.py`，具体设计写在 `tools/designs.py`，
技术发展路线写在 `tools/techroad.py`（叙述）与 `tools/techparams.py`（参数 + 配图引用，图在 `techfigs.py`），
创业者路线图写在 `tools/ventures.py`，板块十的图写在 `tools/synthfigs.py`，
由 `tools/build.py` 生成 `index.html` 与 `sections/*.html`。
**改内容只改 Python 数据文件，不要手改生成的 HTML。**

新增一类内容的标准做法：**放一个新模块，用 slug 挂载**，不要动 `content_*.py`。
`build.py` 里统一挂并在导入时断言，漏配会在构建时直接报错：

```python
for _b in BOARDS:
    _b['chain']    = CHAINS.get(_b['slug'])
    _b['cost']     = COSTS.get(_b['slug'])
    _b['design']   = DESIGNS.get(_b['slug'])
    _b['techroad'] = TECHROADS.get(_b['slug'])
    _b['venture']  = VENTURES.get(_b['slug'])
    if not _b.get('layers', True):      # 收口板块（板块十）不套五层模板
        continue
    assert all(_b[k] for k in ('chain', 'cost', 'design', 'techroad', 'venture')), \
        f'板块 {_b["slug"]} 数据缺失'

# 技术路线再挂一层：按 (slug, 步号) 把参数与配图填进每一「步」
for _b in [b for b in BOARDS if b.get('layers', True)]:
    for _i, _s in enumerate(_b['techroad']['stages'], 1):
        _m = STEP_META[(_b['slug'], _i)]
        _s['params'], _s['fig'] = _m['params'], _m['fig']
```

页面里五层的排列顺序由 `build_section()` 决定，目前是
**技术链路 → 具体设计 → 技术怎么一步步做 → 创业者路线图**，
侧栏目录顶部对应四项不带编号的概览项（不与 N.1 / N.2 的编号体系冲突）。

## 板块开头的导览（给第一次看的人）

每个板块页最前面有一个「先看两张图」的导览区，用**同一套框架**回答两个问题——
这是刻意的：读者读完第一个板块，就学会了怎么读后面八个。

| 图 | 回答的问题 | 形式 |
|---|---|---|
| 导览图 1 | 这个领域在解决什么问题 | 一条主线链（`flow`） |
| 导览图 2 | 现在走到哪一步了 | 三档进展（`layers`）：已做到 / 在验证 / 还在纸上 |

- 数据在 `tools/introfigs.py`，按 `(slug, 1|2)` 索引；**十个板块都有**（含收口页）；
- 三档沿用全站正文的既有框架（首页 dek 里那句「已经做到的 / 正在验证的 / 还只在纸上的」），
  所以导览图与正文是一个口径，不是两套说法；
- 收口页（板块十）的第二张换了形式：用成熟度横条画出「三个前提今天一个都不成立」，
  比文字更有冲击力；
- 构建时断言十个板块各两张；`check_site.js` 还断言**导览区必须排在所有章节之前**——
  它是入口，跑到中间去就失去意义了。

写作口径：**句子短、不用缩写、专业词第一次出现时就地解释**。
导览是给「不知道比冲、不知道什么叫闭环生保」的人看的，不能假设读者懂任何东西；
这与后面几层（写给同行看）的密度是**刻意不同**的——不要为了统一而把导览写难。

## 技术链路

每个板块页开头都有一条「技术链路」，回答两件事：**这个领域最先进的方法是什么**，
以及**它具体可以怎样实现**。

- **最先进的方法**：每个板块点名一种前沿方案（例：板块五是「激光推进光帆」，
  板块八是「近地小行星原位资源利用」），并说明它和别的路线差在哪。
- **技术链路**：把该方案拆成 6 个必须按顺序打通的环节，每个环节写清**怎么实现**——
  工程手段、关键参数、需要突破的点。
- **成熟度标注**：每个环节标出当前状态（**已实现 / 在验证 / 待突破 / 物理约束 / 仅纸上**），
  方便一眼看出哪些是工程问题、哪些是物理上就改不了的。
- **最难的一环**：点明这 6 环里哪一环最决定成败，以及为什么。

`tools/chains.py` 里每个板块的字段：

```python
"slug": dict(
    frontier="这个领域最先进的方法",
    lead="为什么这条路线算最先进",
    nodes=[dict(t="环节名", s="成熟度", how="具体怎么实现")],   # 固定 6 环
    bottleneck="最难、也最决定成败的那一环",
)
```

成熟度取值只能是 `done` / `run` / `hold` / `lock` / `plan`，
构建时会校验环数必须为 6、成熟度取值必须合法。

### 每一环展开：技术详解 + 创业视角

`chains.py` 里每环只有一句话（标题 / 成熟度 / 怎么实现），页面上每一环下面还会再展开两块：

- **技术详解**——这一环实质在做什么、关键参数与判据、当前做到哪一步、真正的难点在哪。
- **创业视角**——这一环的商业形态（卖设备 / 卖服务 / 卖数据 / 卖软件）、客户与付款方是谁、
  创业者能站在哪个位置、窗口期为什么是现在、以及**典型死法**。

这两块单独放在 `tools/chainbiz.py`，按 `(slug, 环号)` 索引——**环的叙述与商业判断分开维护**，
商业环境变化比技术描述快得多：

```python
CHAIN_BIZ = {
    ("current", 3): dict(
        detail="这一环的技术详解",
        biz="这一环的创业视角，末尾给一条「死法」",
    ),
    # …共 54 条（9 板块 × 6 环）
}
```

构建时会断言 `chains.py` 的每一环在 `chainbiz.py` 里都有对应条目、且 `detail` 与 `biz` 都非空。

写创业视角的三条口径：

1. **优先看上下游，不看总体。** 整箭、整星、整发动机是国家级资本与十年周期的游戏，
   创业者的位置在耗材、检测、软件、服务这类「大机构不愿意自己从头做」的活上。
2. **该说没有就说没有。** 有些环（如光速推进的激光阵列）不存在创业公司能承担的商业形态，
   这时写的是「这一环的创业机会在它上游的某块使能技术」，而不是硬凑一个赛道。
3. **每一环都要给一条死法。** 只说机会不说怎么死的商业判断没有价值。

### 每一环也配一张「链路图」（共 54 张）

定位要与「技术怎么一步步做」那层的配图区分开，**两层不要画同一件事**：

| 层 | 配图回答的问题 | 视角 |
|---|---|---|
| 技术怎么一步步做 | 这一步**怎么推进**（从今天的基线到目标） | 纵向：路径 |
| 技术链路 | 这一环**现在是什么样、卡在哪** | 横向：现状切片 |

- 数据在 `tools/chainfigs.py`，按 `(slug, 环号)` 索引；渲染由 `render_chain()` 调 `render_chain_fig()`；
- 编号用「链路图 1..6」（层内序号），与技术路线层（无编号）、创业者路线图（理论图 1..6）、
  板块开头（导览图 1..2）全部区分开；
- 构建时断言「九板块 × 6 环」齐全；`check_site.js` 断言每个板块页恰好 6 张。

**这一层的写作口径是「通俗易懂」**——它的读者面最杂，所以：

- 一图只讲一个信息点，优先用进度、对比、流程这类不需要背景知识的形式；
- **能给出数字就给数字**：数字比形容词可信（「推力可降到约 40%」比「深度节流」清楚得多）；
- 第一次出现的概念就地解释，例如「入轨的门槛是速度而不是高度」、
  「98% 的意思是每 100 升水只补 2 升」；
- **量级差太大时用对数刻度**（`dia.logscale`）。例：把「100 吉瓦」和「一座电站」
  放在线性刻度上什么都看不出来，换成对数刻度，「≈ 四座三峡的装机」一眼就懂。

⚠️ 两个坑：

1. **折线图的 y 轴固定从 0 起**，所以「两组数据都接近 100%」时差异完全看不出来
   （我拿 92% vs 68% 试过，两条线挤在顶部）。这种情况要换指标——
   改成「累计飞行次数 + 一条兑现线」，差异立刻清楚。
2. **`layers` 条目多（4 项）时，说明行会压到最后一项、甚至出框。**
   坐标要由项数推出来：每项递进 `14（有说明时）+ row`，据此算画布高度。

## 要花多少钱

每条技术链路后面都跟一张成本表，按 slug 从 `tools/costs.py` 取：

```python
"slug": dict(
    items=[dict(t="项目", a="金额", n="口径与说明")],
    scale="整条链路的总量级（一句话）",
    note="口径提醒：金额来源、区间、汇率换算依据",
)
```

口径约定：

- 金额单位统一为**美元**，因为原始来源全部是美元计价；只在有实际参考意义时才给人民币换算
  （按约 7.2 元人民币/美元）。
- 同一项目不同来源差异可能达到数倍，**凡有区间的一律给区间，不取单点值**；
  报价（牌价）与成本（边际成本）必须分列，不能混为一谈。
- 成本表用 `table.cost`，它的列宽只在 `min-width:641px` 生效——
  写进移动端会覆盖卡片化的 `td{width:100%}`，把卡片压窄。

## 具体设计

每个板块在技术链路与成本之后，还有一节「具体设计」：**这个最先进的方法具体怎么做**。

- **三维等轴测图**：`tools/iso.py` 是自写的等轴测投影器（把 3D 长方体 / 圆柱 / 圆台投影成
  矢量 SVG），九张图共用同一套几何与配色。矢量图可打印、无外部依赖，比位图渲染更适合工程示意。
- **设计参数表**：7 行，每行给「参数 / 取值 / 为什么是这个值」——只有数值没有理由的表没有意义。
- **设计分解**：子系统 → 做什么、关键指标。

`tools/designs.py` 里每个板块的字段：

```python
"slug": dict(
    headline="设计目标（一句话）",
    specs=[dict(k="参数", v="取值", n="为什么是这个值")],
    subs=[dict(t="子系统", n="做什么 / 关键指标")],
    scene=<返回 SVG 的函数>,      # 用 iso.py 搭
    caption="图的说明（放 figcaption，不要画进 SVG）",
    note="设计说明：取舍、不确定性",
)
```

### 画等轴测图的几条硬规矩（改图前必读）

1. **只有 (x − y) 不同才会左右分开。** 坐标是 `u = (x−y)·cos30`、`v = (x+y)·sin30 − z`。
   把两台泵写成 `(±34, ±34)`，它们的 x − y 都是 0，会在屏幕中轴上叠成一个。
   要横向铺开就固定 `y = 0`、只变 `x`。
2. **标注一律往屏幕水平方向延伸。** 用 `roff(p, d)` / `loff(p, d)` 按物体坐标算锚点，
   别手填 `R()` / `L()`——手填很容易让文字压在别的物体上。
3. **同一侧的标注要让 `v` 彼此拉开 ≥18 个单位**，否则文字会叠在一起。
4. **长句一律放 `caption`**，不要 `g.note()` 画进 SVG：SVG 里的文字无法自动换行，长了就被裁。
5. 画完必须跑自检（同时报「文字出框」和「文字互相重叠」）：

```bash
python3 tools/check_designs.py
```

自检比肉眼看可靠得多——本轮的三个 bug（缩放只会缩不会放、缩放解漏掉右边缘约束、
三条左侧标注 `v` 相同叠在一起）全都是它先发现的，截图上看不出来。

## 技术怎么一步步做

每个板块还有一节「技术怎么一步步做」——这一层是**纯工程视角**：
从今天的技术基线出发，分五步推到目标状态，每一步具体做什么。

与「创业者路线图」的分工要分清：那一条讲「一家公司怎么活下来」（商业），
这一条讲「一项技术怎么被做出来」（工程）。

结构是 **今天在哪 → 要到哪 → 五步 → 最硬的一关**：

- **今天在哪 / 要到哪**：左右对比条，先把起点和终点摆清楚。
- **五步**：每步是一张完整的卡片，含
  `阶段名 / 时间量级 / 要跨的差距 / 怎么做 / 配图 / 技术参数表 / 需要的条件 / 通过判据`。
- **最硬的一关**：五步里哪一步最可能卡死，以及为什么。

**每步的配图按内容选形式**（9 板块 × 5 步 = 45 张）：

| 内容 | 用什么 | 生成器 |
|---|---|---|
| 装置、结构（发动机剖面、在轨加注、塔架、种植舱…） | 等轴测立体图 | `tools/iso.py` |
| 过程、数值、层级（摊销曲线、对数刻度、流程链、时间条…） | 二维概念图 | `tools/dia.py` |

图写在 `tools/techfigs.py`，键名与 `techparams.py` 里的 `fig` 字段一一对应。
二维图有现成模板可以直接调：`series`（折线）、`logscale`（对数刻度尺）、
`flow`（流程链）、`stack`（堆叠柱）、`timeline`（时间条）、`scatter`（散点）、`layers`（分层）。

**参数与叙述分两个文件维护**：`techroad.py` 是叙述（为什么这么做、判据是什么），
`techparams.py` 是数值（参数名 / 取值 / 口径）。两者更新节奏不同——
叙述较稳，数值会随公开资料修订——分开写互不影响。
`build.py` 用 `(slug, 步号)` 把两者挂在一起，并断言 45 步都有参数与图。

⚠️ 二维图的文字坐标是**手写像素**，最容易出的错是「出框」和「互相重叠」——
所以 45 张图必须跑自检：

```bash
python3 tools/check_figs.py
```

它会算出每张图里所有文字的像素矩形，两两求交，同时报出框与重叠。
本轮做出的 12 个真 bug（图例压标题、x 轴名压注释、数值被推出画布、
时间条跑出网格、尺寸线压在主体上……）**全部是它先发现的，截图看不出来**。

时间量级字段同时兼作状态位：`已走完`（绿）/ `在推进`（蓝）/ 其余按年计的为灰。
渲染时由 `_stage_w_class()` 按开头词判定，所以**写数据时请沿用这三个前缀**。

`tools/techroad.py` 里每个板块的字段：

```python
"slug": dict(
    now="今天的技术基线：现在能做到什么，卡在哪",
    goal="目标状态：要把它做成什么样",
    stages=[dict(p="阶段名", w="时间量级", gap="要跨的差距",
                 do="具体怎么做", need="需要什么条件", gate="通过判据")],
    hard="最硬的一关，以及为什么",
    note="口径提醒",
)
```

构建时会断言每个板块恰好 5 步、且六个字段都不为空。

**写作原则（与创业者路线图一致，别写成宣传文案）**：

1. **每一步都要有「通过判据」**，而且必须可观测——试车时长、复用次数、回收率、σ 值，
   不是「完成度 80%」这种没法核对的表述。没有判据的「推进」只是口号。
2. **已走完的阶段也要写，并标明「已走完」**。路线图从今天的真实位置起画；
   省略已走过的路，读者就不知道当前位置是怎么来的、为什么是这个顺序。
3. **区分「工程问题」与「物理约束」**。物理上无解的（光帆没有减速、
   光速决定的通信往返时间）要明说不可解决，不要写成「待突破」——
   这两类混在一起会让人误以为只要投入资源就能解决。
4. **写清路线选择理由**比堆参数更有价值（为什么选液氧甲烷、为什么选目标看 Δv 而不是成分）。

## 创业者路线图

每个板块最后还有一节「创业者路线图」：**如果要从零做这件事，该怎么一步步走**。
从判断到动作一共四层，其中最后一层是**和方向无关的通用流程**：

- **切入点**：一句话给出最适合新公司的位置。
- **赛道判断**：动手前必须先搞清的六件事——`客户与付款方 / 钱从哪来 / 市场量级 /
  竞争格局 / 护城河 / 这类公司的整体死因`。渲染成六格细线网格。
  这一层的价值在于**它回答的是「该不该做」，而不是「怎么做」**：
  很多方向技术可行、但客户只有三五家、或者钱只能来自政府项目，
  这些判断放在「五个阶段」里讲会被动作细节淹没。
- **五个阶段**：每阶段九个字段——
  `阶段名 / 时间量级 / 做什么 / 具体怎么做 / 卖什么给谁 / 这一步要投多少 / 通过判据 /
  这一步的死法 / 止损线`。四格元数据（2×2）+ 一条单独的止损线。
- **最该避免的事**：这个方向最常见的错误下注。
- **「零基础起步」通用手册**：十个步骤，九个板块共用。

**这一层有两种读者，所以内容分成两块。**「赛道判断 + 五个阶段」是写给懂行的人的——
它回答「这条赛道值不值得做、该从哪儿切进去」；而真正没开过公司的人会卡在更前面：
客户名单从哪来、第一封邮件怎么写、合同谁拟、股权怎么分。所以补了两样：

| 补的东西 | 解决什么 | 在哪 |
|---|---|---|
| **每步的「具体怎么做」** | 操作层：去哪找、见谁、说什么、备什么材料、花多少钱。与上面的「做什么」在视觉上分开（浅底 + 层色竖线） | `tools/venture_how.py`，9 板块 × 5 步 = **45 条** |
| **「零基础起步」通用手册** | 与方向无关的通用流程：适配度自查、注册公司、找第一个客户、报价与回款、签合同、找人与分股权、管现金、何时融资、何时收手 | `tools/founder101.py`，**10 节 / 49 条动作**，默认折叠 |

通用手册九个板块**共用同一份**，放在整层末尾的折页里。为什么折叠：它六千多字，
展开会把领域内容淹掉；为什么不能不放：这些恰恰是新人最缺、又和方向无关的常识。
打印时由 `site.js` 的 `beforeprint` **全部展开**——纸上没有「点开」这个动作，
打出一根点不动的标题条毫无意义（`check_print.py` 之外，还专门抽查过 PDF 里
「注册公司」那一节确实落在纸上）。

写作要求（决定了它到底有没有用）：每一项都要有**可执行的动词**和**数字量级**——
「材料做 3 页 A4 + 一张表」「邮件只写五句话」「第一单几十万元量级」
「4 天后打一次电话，之后每两周一次、至少跟 6 次」。
「要重视客户关系」这种正确但没用的句子一律不写。

两份数据分开放（判断层 `ventures.py`、动作层 `venture_how.py`）是因为修订节奏不同：
判断几年才动一次，动作会随市场反复调。`ventures.py` 导入时**逐条断言两边条数一致**，
少一条就当场报错——不能让某一步静默地没有操作层。

**「止损线」与「死法」是两回事，别合并。** 死法是客观风险（这一步会怎么死），
止损线是你的动作（出现什么信号就该放弃）。前者是认知，后者是纪律——
只有前者的话，读者知道了风险却不知道该在什么时候退出。

**每个板块配 6 张理论图**（赛道判断 1 张 + 五个阶段各 1 张，共 **54 张**）：
图回答的是「为什么这样成立」——机制、权衡、依赖、时机，
区别于「具体设计」那一层的装置图（那层回答「长什么样」）。

- 数据在 `tools/theoryfigs.py`，按 `(slug, 部位)` 索引，部位是 `'track'` 或 `1..5`；
- 渲染由 `render_venture()` 调 `render_theory_fig()`，图注编号是**层内序号**
  「理论图 1..6」——刻意避开「图 01」（具体设计）与「图 10.1」（收口页）两套编号，防止读者混淆；
- 构建时断言「九个板块 × 6 个部位」全部有图，漏一张就报错；
- `check_site.js` 断言每个板块页恰好 6 张理论图；
- 图容器直接复用 `.trs-fig`（技术路线的配图样式），没有新增 CSS。

⚠️ 画理论图时最容易踩的两个坑（已用自检堵住，但知道原因能省时间）：

1. **象限图 `scatter` 的 `quad` 文字固定画在中线右上角。** 点的标签如果落在那个位置就会被压住。
   自检报重叠时，**先把点挪开，而不是删掉 quad**——那句象限说明本身是有信息量的。
2. **时间条 `timeline` 的起止下标不能超出 `xlabels` 的范围**（下标是 `0..n-1`，不是百分比）。
   超出会画到画布外，表现是「条内文字出框」，而条本身看起来完全正常。

另外，`hbars` 的 `row` 是**含说明行的总行高**，传小了说明行会顶到下一行；
条目少（2–3 行）时记得把画布高度调小，否则底部会留一大片空白。

`tools/ventures.py` 里每个板块的字段：

```python
"slug": dict(
    entry="切入点（一句话）",
    lead="为什么从这里切，而不是从最显眼的地方切",
    track=dict(customer="客户是谁、谁付钱", money="钱从哪来、什么节奏",
               market="市场量级（诚实口径）", rivals="竞争格局：谁已经在做",
               moat="护城河从哪来", fatal="这类公司的整体死因"),
    steps=[dict(p="阶段名", w="时间量级", do="做什么",
                mode="卖什么给谁、怎么收钱", gate="通过判据（可核对）",
                burn="这一步要投多少、要什么人", kill="这一步的死法",
                stop="止损线：什么情况下该放弃")],
    avoid="最该避免的事",
    note="口径提醒",
)
```

结构由 `build.py` 的 `render_venture()` 渲染，`TRACK_FIELDS` 决定六格的顺序与标签；
构建时断言「九个板块都有 track 六项、每个阶段都有八个字段、标签数是 5×5=25」。

⚠️ **标签一律用 `<span class="lb">`，不要用 `<b>`。** 正文里的加粗也用 `<b>`，
一旦给标签配上 `display:block`，正文里的加粗会跟着变成块级——
加粗那句独占一行、后面的标点被甩到下一行。这个 bug 构建和图自检都抓不到，
只有截图能看出来，所以 `check_site.js` 里加了一条专门断言：
「块级 + 内容超过 12 字」的 `<b>` 就是被误当标签的正文加粗。

**内容立场（写内容时守住，别写成招商广告）**：

1. 优先推荐上下游的**耗材 / 检测 / 软件 / 服务**，而不是整机与总体——
   整箭、整发动机、整星都是国家级资本与十年周期的游戏，新公司进不去。
2. 没有商业路径的方向（光速推进、人体冬眠）**直接说「这不是创业赛道」**，
   然后给出真正能做的使能技术。宁可劝退，不要给人虚假希望。
3. 每一步都要写「死法」，并给一条「止损线」。
4. 「地面收入养航天研发」是出现频率最高的可行结构——
   航天客户预算大但节奏极慢，纯航天定位的公司活不到量产。
5. 金额一律给量级，并说明是公开数据还是估算；**没有公开数据的就直说
   「没有第三方统计」**，不要编一个看起来专业的数字。
6. 客户数量少的方向要明说客户数（如「全球相关客户不超过二十家」）——
   「市场规模」在这种行业里不是有用的指标，该问的是「这个客户一年花多少」。

## 星船总体设计（板块十，收口）

前九个板块各自回答一个领域的问题；板块十**不引入新的外部数据**，只把前面九个的条件收拢成
一版可讨论的总体设计。七节的行文顺序就是推导顺序：

| 节 | 回答什么 |
|---|---|
| 10.1 从九个板块推出设计约束 | 九个板块是**依赖关系**不是并列清单；三条物理边界直接划掉整类方案 |
| 10.2 总体构型 | 为什么必须分体串联 + 在轨加注（由 10.4 的质量比反推） |
| 10.3 舱段布局 | 七段为什么按这个顺序排（管路要短 / 无人区与有人区要隔开 / 屏蔽质量要集中） |
| 10.4 质量账 | 用**火箭方程算**质量比，得出「加注不是优化项而是前提」 |
| 10.5 分系统技术要求 | 八个分系统：要求 / 依据来自哪个板块 / 今天的真实状态 |
| 10.6 设计权衡 | 五对互相打架的要求，以及设计上实际怎么让步 |
| 10.7 一版基准配置与三个前提 | 配置表 + 哪三个条件不成立就全盘不成立 |

**这个板块的三条写法约定：**

1. **不套五层模板。** 板块 1–9 是「领域页」，板块 10 是「综合页」，硬套会把并不存在的内容塞进来。
   `build.py` 用 `layers=False` 跳过五层装配断言。
2. **图长在正文中间。** 别的板块是「一层一图」，板块十的图属于具体小节，所以正文里写
   `{{FIG:key}}` 占位符，`build.py` 的 `render_figs()` 按出现顺序替换成 `<figure>` 并编成
   图 10.1 / 10.2 …；图仍然集中在 `tools/synthfigs.py` 里维护。
3. **结尾给「条件清单」而不是「计划」。** 10.7 列出三个前提（在轨加注、冬眠、辐射防护），
   并明说**今天一个都不成立**——把「技术不够成熟」这种模糊判断换成三条各自有明确判据的条件，
   这才是把九个板块合起来看唯一能得到的收获。

⚠️ **占位符替换必须显式调 `.svg()`。** `spec['make']()` 返回的是图对象（`Iso` / `Dia`），
不是 SVG 字符串。直接插进 f-string 会渲染成 `<iso.Iso object at 0x…>`——被浏览器当成未知标签丢掉，
页面上留下一个**空图框 + 正常图注**，而且全程不报错。`render_figs()` 里已加断言堵死这条路。

## 层级路标：六层概览 vs 板块正文

一个板块页有九个小节，但它们是**两类东西**：

| | 是什么 | 每页数量 | 标题样式 |
|---|---|---|---|
| 六层「概览栏目」 | 导览 / 技术链路 / 具体设计 / **虚拟模型** / 技术怎么一步步做 / 创业者路线图 | 6（收口页只有导览 + 虚拟模型 2 层） | 24px，带「层 01–06」序号块，左竖线与分隔线取**层色** |
| 带编号的「正文小节」 | 2.1 / 2.2 …（这个板块自己的细节） | 4–8 | 19px，墨黑竖线，无序号块 |

**为什么必须分开**：这两类原来用的是同一套 `section` + `h2`，视觉上完全同位。
加完 179 张图之后一个板块页接近两万像素，读者滚到中段就分不清「这是栏目开头还是某个小节」。
现在的做法是三件事一起上：

1. **层序号块**（`<span class="ly"><i>层</i>01</span>`）——区分主要靠它，不靠颜色。
2. **层色的分隔线**——每层上方一条通栏发丝线，线左端 56px 取层色；
   第一层紧跟在首屏控制台之后，不画线（否则会把控制台和内容割开）。
3. **正文之前的分组标题**（`.grp-hd`，墨黑短棒 + 「正文 / IN DETAIL」）——
   它必须排在**所有层之后**，`check_site.js` 会断言这一点（跑到层前面，「正文」这个词就没有意义了）。

**层序号是「页内」连续的，不是全局的。** 收口页不套六层模板，只有导览与虚拟模型两层；
若沿用全局层号会显示成「层 01」「层 04」——中间两个号在本页根本没出现，读者只会以为漏了内容。
所以 `build.py` 里有一张 `b['_lmap']` 把全局层号映射成页内连续编号（九个板块页是恒等映射）。
`check_site.js` 随之改成断言「层序号在**本页**从 01 连续递增」。

侧栏也照着分两组：层项带层色小方块，然后是「正文 · 板块细节」分隔，再是编号小节。
⚠️ **分组依据是 TOC 数据里的 `layer` 字段，不能靠「有没有编号」判断**——
板块一的正文小节本来就没有编号（`sub=True` 的阶段条目），靠编号判断会把它们全当成层。

### 层色阶：位置色 ≠ 状态色

```
--ly1:#4a6b83  --ly2:#356b8a  --ly3:#256b7e
--ly4:#1c6a72  --ly5:#1a6a68  --ly6:#17665c
```

从石板蓝到青的**同族色阶**，专用于「这是第几层」这个**位置**信息。
**刻意不用绿 / 蓝 / 琥珀 / 红**——那四个是全站的**状态**语义色（已实现 / 在验证 / 待突破 / 物理约束），
层色再借用它们，读者就会把「第 3 层」误读成「待突破」。六个色的明度刻意做得接近，
所以每一档的对比度都够（实测层序号块 5.4:1），区分靠序号而不是靠色相。
加第六档时把逐档亮度步长从 0.045 收到 0.036——六档全展开后最亮那档对 `--page` 只剩 4.79:1，
再大就压到断言的 4.6 线附近了（`boardskin.check()` 会在构建期拦住）。

改这一层时守两条：**层色只出现在小面积标记上**（序号块、56px 短线、侧栏小方块），
不要拿它去铺大底色；**不要为了「更好认」把六档拉开成六种色相**，那会让页面变成调色盘。

## 虚拟模型：可拖拽旋转的 CSS 3D

每个板块页在「具体设计」之后有一层「虚拟模型」：**一个能拖拽旋转的三维模型** + 编号图例，
再配一张「虚拟视图」（把该板块的装备放进仪表框里看它**跑起来是什么样**）。

- 模型数据在 `tools/modelrigs.py`（十一个：十个板块各一 + 收口页的整船分解图）；
- 渲染器在 `tools/models3d.py`；虚拟视图在 `tools/virtualviews.py`；
- 交互在 `assets/site.js` 第 8 节，样式在 `assets/site.css` 末尾。

### 为什么不用 Three.js

全站是有意「纯静态、零依赖」的（手写内联 SVG + 原生 JS）。Three.js 是 600 KB 的外部库，
会破坏这条线，而且和手绘矢量图不是一套质感。CSS 3D 用的是浏览器自带的变换管线，
产出就是 div：**打印、缩放、可访问性、`prefers-reduced-motion` 全都白拿**。

代价是要自己写投影与自适配，下面几条都是踩出来的。

### 图元与纹理：精细度只有两条路

「模型再精细一点」落到实现上，只有两条路，而且**必须一起走**：

| 路 | 做法 | 收益 |
|---|---|---|
| **形状** | 加图元，让外形能表达准 | 从「方块 + 圆柱」升级到锥台、穹顶、环形箍、四棱台、钟形喷管、弧形贴片 |
| **表面** | 加纹理，给大面铺细节 | **零面片成本**：一张板贴一层 CSS 渐变就有了焊缝／瓦缝／格栅 |

现有图元（全部用同一套 `_face` + `rotateY/X/Z` + `translateZ` 表达）：

| 图元 | 用途 | 关键点 |
|---|---|---|
| `box` | 机箱、梁、翼面骨架 | 六个面各一张 |
| `cyl(axis=)` | 筒体、管路、滚轮 | `axis='x'/'z'` 可横放；`segs` 沿轴分段 |
| `frustum` | 鼻锥、喷管扩张段、抛物面天线 | `segs` 分段 + `clip-path` 裁出精确梯形 |
| `dome` | 贮箱端头、球冠 | 半径按 cos、高度按 sin 收口 |
| `nozzle` | 钟形喷管 | 半径按 `t**1.7`；默认带管束纹理 |
| `taper` | 翼面、整流罩、渐缩段 | 四棱台，四个侧面是**真梯形**（`clip-path`） |
| `ring` | 法兰、对接环、监护环 | `inner=False` 只留外壁 + 上环面，面片减半 |
| `sphere` | 球罐、关节 | 纬向切带，`n×nv` 就是面片数 |
| `arc` | 热盾瓦片区、舷窗带 | 只占圆周一段；锚点在弦中点，靠 `off` 摆位 |

九种纹理：`seam` 环焊缝、`rib` 加强筋、`tile` 瓦片、`plate` 蒙皮拼板、`grid` 格栅、
`slat` 百叶、`tube` 冷却管束、`dot` 点阵、`stripe` 斜纹。纹理由半透明黑 + 半透明白叠成，
所以它是「同一块材料在不同受光下」，而不是贴上去的一层死色。

**⚠️ 该用几何的地方别用纹理。** 这是这一轮最贵的一课：环焊缝一开始是用 `seam` 纹理画的，
但一圈上相邻面片的倾斜角不同、屏幕上的周期就不同，一条横线穿过十几个面片之后累计错开
好几个像素，整根箭体看着像**砖墙**。真正的解法是 `cyl` 的 **`segs` 分段**——段与段之间是
**真的 3D 棱线**，随旋转正确变换。纹理现在只负责补更细的那一层。

另外两条手感上的经验值：

- **明暗差别拉太大。** 一圈十几个面片，相邻两片法线差十几度，光照系数给到 0.64 就是一层
  竖向条纹，圆柱看着像棱柱。压到 0.46 既能看出圆、又不会把「筒」切成一瓣一瓣。
- **回转体的侧面片不要描边**（`noedge`）。每条边都算一条竖线，叠起来同样会盖掉横向的环焊缝；
  改成几乎同色的描边，只起「防止相邻面片漏出背景」的作用。

### 三条必须一起成立的事

1. **每个面片必须以「部件原点」为中心。** `.m3d-p` 是 0×0 的绝对定位元素，
   里面的 `.m3d-f` 写 `left:50%;top:50%` 得到的**就是原点**，再靠生成期写死的负 margin 对中。
   ⚠️ **不能改用 `transform: translate(-50%,-50%)` 去对中**：transform 整串是绕元素自身中心
   应用的，那样旋转就绕错了点，面片会像扇子一样飞出去。
2. **`--m3d-k`（窄屏缩放）必须挂在 `.m3d-stage` 上**，不能挂 `.m3d-world`——
   编号点那一层是 world 的**兄弟节点**，挂在 world 上它就取不到，窄屏下会模型缩小、标注不缩。
3. **编号点是 2D 覆盖层，不放进 3D 世界。** 放进去转到背面会被不透明的面片挡住。
   做成覆盖层则永远可读；位置用与模型同一套投影公式算：没有 JS 时用的是**生成期按默认角度
   算好写进 HTML 的 left/top**（所以禁用脚本、打印都是正确的一帧），有 JS 时逐帧更新。

### 平滑着色：让"一圈平面"看起来是圆的（这一版最关键的一步）

上一版把图元做齐了、零件数翻了三倍，但圆柱、穹顶、球看起来还是**积木**。
问题不在零件数量，在着色：每个面片只有一个平色，一圈十几个平面、相邻法线差二十几度，
拼起来就是一根棱柱。

真实 3D 的做法是**平滑着色**（Gouraud）——明暗按法线算，在面片**内部插值**。
CSS 可以精确复刻：给每个回转面片一条 `linear-gradient`，两端取**相邻面片**的明暗、
中间取自己的。一圈面片在视觉上就接成了连续曲面，而几何仍然只是平面。

三个分量：环境 + 漫反射 + **高光**。最后一项是「金属感」的来源——没有它模型像塑料。
高光是 ≤8 次幂的窄带，幂次**不能给大**：一圈就十几片，窄到不足一片会变成
「某一片特别亮」的亮斑，比没有高光更假。

配套三件事，缺一样就白做：

| 改动 | 为什么 |
|---|---|
| **面片真的倾斜** | 见下一节。竖直平面 + 裁剪是糊不出锥面的 |
| **侧面片描边改透明** | 一圈十几条硬描边叠起来同样是竖线，会把刚接好的曲面又切碎 |
| **`background-origin:border-box`** | 默认 `padding-box` 会让渐变只铺到内容区，最外 1px 露出平色 `background-color`。面片只有十来像素宽，**这 1px 就是一条清楚的竖线**——而它在 CSS 里，构建期断言看不见，是靠浏览器侧的 `getComputedStyle` 抓到的 |

### 面片必须沿轮廓倾斜，不能靠裁剪假装

第一版做锥面的办法是：面片永远是竖直平面，放在平均半径处，再用 `clip-path` 把上边裁窄。
**裁剪只让顶边变窄，没有让它往轴心靠**——顶边仍然停在平均半径上。于是一段段叠起来，
穹顶变成一层层带缺口的「婚礼蛋糕」，鼻锥、喷管、抛物面碗全是这个问题。

正解是让面片自己的平面沿轮廓倾斜：

```
tilt = atan2(−Δr, Δy)        # 半径—高度平面里的轮廓倾角
h    = hypot(Δr, Δy)         # 高度取**斜边长**，局部 +y 正好沿轮廓走
z    = rm / cos(tilt)        # translateZ 沿倾斜后的法线走，要除掉 cos
off_y = (y0+y1)/2 − rm·tan(tilt)   # 再把多出来的竖直分量补回来
```

倾斜后局部法线正好等于锥面的真实法线 `(Δy·sinθ, −Δr, Δy·cosθ)`，
所以明暗、高光、穹顶的「顶上亮」全部自动正确，不用再单独算一遍。

⚠️ **`atan2` 的符号要按 CSS 取反**：CSS 里元素局部 `+y` 是**向下**的，
「沿轮廓往上」在 CSS 的 +y 里是往下，所以是 `atan2(−Δr, Δy)`。
写反的症状很有欺骗性：面片位置大致还对，只是**法线上下颠倒**——
穹顶变成「底下亮、顶上暗」，而包围盒断言是全绿的。这一条现在是靠**接缝断言**拦的。

### 断言又升级了三处（都是被负向测试逼出来的）

上面这些机制有个共同点：**失效时几何、包围盒、面片数都可能还是对的**。
所以断言从「比极值」往「比结构」走：

| 断言 | 查什么 | 拦的是 |
|---|---|---|
| **接缝** | 同一方位角上，前一段的上边中点要与后一段的下边中点重合；**两段的边宽也要相等** | 面片高度取了竖向高度而不是斜边（每段短掉 cos(tilt)，段间开缝）；裁剪基准半径取错 |
| **收口方向** | 裁剪把上边裁窄了（w_top < w_bot），上边的半径就必须更小 | 倾斜角符号写反——整段「倒扣」，该收的地方在放 |
| **平滑着色覆盖率** | 每个部件里带渐变的回转面片占比 ≥80%（显式 `flat` 的弧面片除外） | 某一个图元整体丢了渐变——只看整模总覆盖率会被别的图元掩盖 |

⚠️ 最后一个断言第一版写错了：判定用的是 `'linear-gradient' in css`，
而纹理用的是 **`repeating-linear-gradient`**，它**包含**这个子串——于是每张带纹理的面片
都判成"有渐变"，负向测试（把渐变改成 `None`）照样全绿，断言等于没写。
改成数差值（出现次数减去 `repeating` 的次数）才生效。

这一轮一共十组负向测试，包括：倾斜角符号、面片高度取错、`translateZ` 没除 cos、
`off` 的竖直修正符号、裁剪基准半径、两个图元各自丢渐变、渲染层不输出渐变、
`taper` 侧面不倾斜、穹顶锚点偏心、描边改回硬棱线。**十组全部确认会让自检变红。**

### 接地影：按默认视角的真实投影算

台面上原本铺的是一块**固定**椭圆阴影，跟模型没关系——高瘦的火箭和扁宽的采矿船用同一个椭圆，
看着像模型浮在别人的影子上。现在按默认视角下几何的投影宽度生成（纵向压扁并夹住上下限，
因为真阴影是斜上方光线打在**地面**上的投影，从斜上方看天然比物体窄得多）。

它单独做一层（`.m3d-shadow`）而不是画在台面背景上：背景没法跟着 `--m3d-k` 缩，
窄屏会拖出一大截。和编号点那一层同一个套路——子元素用「50% + 设计像素」定位，
外层整体 `scale(var(--m3d-k))`。

### 静默画歪的坑（构建全绿、只有截图能看出来的那类）

这一轮最贵的三条教训，都属于「断言写得不对 = 等于没写」：

| 坑 | 症状 | 现在靠什么拦住 |
|---|---|---|
| **变换字符串提前拼死** | `box()` 里就把 `translateZ(13px)` 拼好了，于是面片长宽按 k 缩放了、位移没有。k≈1.14 的星舰完全正常，**k=3.44 的机器人崩成一张十字展开图** | 自适配按旋转范围采样，所以 `k` 在 1.1–3.4 之间浮动；改成存 `(轴, 角度) + 距离` 参数、渲染时才乘 k |
| **端盖漏一个分号** | `border-radius:50%` 后面忘了 `;`，整条样式变成 `border-radius:50%transform:rotateX(...)`——`border-radius` 吃掉整个非法值，**后面的 `transform` 声明整条丢失**，圆柱端盖全变成贴在原点的方块 | 「从生成的 HTML 里反解面片数」：几何定义 52 张、只反解到 48 张 |
| **断言复用内部变量** | 第一版自检直接拿 `fc['z'] * k` 算，等于把同一份数算两遍。把 `translateZ` 的缩放**故意去掉**，断言照样全绿 | 自检改成**只认 `_faces_html()` 真正吐出来的文本**（正则反解 width/height/margin/transform），并用三组负向测试验过它真的会红 |

`modelrigs.py` 的自检现在查八件事：**任何角度下几何体与编号点都在台面内**、
**默认角度下编号点不重叠**、**每个部件的渲染包围盒与它的几何范围一致**（逐部件，不是只比整模）、
**渲染参数逐项等于几何定义 × k**、**面片数对得上**、**部件锚点落在几何中心**、
**回转面分段首尾相接**、**收口方向与裁剪一致**、**平滑着色覆盖率**；
再加上**装配路线图的分组覆盖性**（见下方「3D 演示路线图」）。

另外两件事：

- **编号点转到某些角度必然互压**——模型转到背面时，前后两个标注会擦肩而过。
  这在坐标上无解（试过挪位置，843 处冲突只挪掉一半）。所以交给运行期：
  `site.js` 每帧按序号优先级把撞上的点淡出，阈值 20px 与圆点直径一致；
  构建期只硬性要求**默认角度不重叠**（那一帧同时是没有 JS 与打印的样子）。
- **台面不能太宽。** 第一版 560×420、自适配目标 340×330，模型只占到台面宽度的三成，
  1px 描边在小尺寸下糊成一片噪点。收到 **460×400 + 目标 400×350** 后模型占到 55%–80%，
  并在 ≥1000px 时把图例挪到右栏，否则右半边会空掉一半。
  ⚠️ 这两个数与 `models3d.py` 的 `STAGE_W/STAGE_H` 是绑死的，`check_visual.js` 会
  断言浏览器**实际渲染出来的台面就是 460×400**——CSS 一改，Python 侧的断言会静默变陈旧，
  只有这条跨语言校验能拦住。

#### 又加了四条之后，断言也跟着升级了两处

零件数翻三倍以后，「一个零件写错、被别的零件挡住」成了主要风险，于是：

| 升级 | 原来 | 现在 |
|---|---|---|
| **包围盒比对** | 只比**整模**的渲染包围盒与几何包围盒 | **逐部件**比。十来个零件里有一个写错，它往往还落在别的零件撑开的范围内，整模一动都不动 |
| **参数一致性** | 只比包围盒 | 从 HTML 反解出的 `width/height/margin/translateZ/off/旋转序列` **逐项**与几何定义 × k 比对。包围盒抓不到的错（比如面片宽高忘了乘 k，而该部件的极值恰好由位移主导）在这里会现形 |

这两条的写法仍然遵守同一条铁律：**只认自己吐出来的文本**，不复用内部变量。
配套的负向测试现在有八组（漏乘 k ×3、宽高传反、旋转序列少一个轴、margin 对中错、
锚点偏离中心、内壁半径写错），每一组都确认过自检会红。

### 点一下放大（聚焦某个部件）

点编号点、点部件本体、点图例项，三种都做同一件事：**把那个部件飞到台面中央并放大，
其余部件压暗留在原地**；再点一次、点台面空白、按 Esc、或点「返回全貌」回到全貌。

- 放大倍数（`data-f`）与「部件中心在哪」（`data-c`）都是**生成期按旋转范围采样解出来的**，
  写在 `.m3d-p` 的 data 属性上，运行期只读不算。扁平部件能放得更大、细长部件小一些；
  上限 6 倍（栅格舵那种小东西再放就没边了）。
- `part`（这个编号点指哪个部件）默认按「到部件包围盒的距离」自动判定，
  但 pin 摆在大部件和小部件之间时它会认错（**实测 55 个点里错了 10 个**），
  所以那几处显式写 `pin(..., part=N)`。
- 构建期断言：任何角度几何与编号点都在台面内、默认角度编号点不重叠、
  **放大后目标部件仍在台面内**、**每个部件的渲染包围盒与几何范围一致**、
  **渲染参数逐项等于几何定义 × k**、反解到的面片数与聚焦参数个数都对得上、
  **每个部件的锚点都落在它的几何中心**（最后这条是聚焦功能的前提：聚焦是把部件的
  `translate3d(锚点)` 丢掉换成 `scale3d`，锚点一偏，放大后就会飞出去）。

#### 四个「看起来能用、其实点不动 / 画歪」的坑

这一轮全踩了一遍，都属于**构建全绿、只有真去点才发现**：

| 坑 | 症状 | 正解 |
|---|---|---|
| **放大整个世界** | 一开始是给 `.m3d-world` 加 `scale3d(k·f) … translate3d(-c)`。数学没错，但邻居跟着一起放大，糊成一片拖影 | 改**部件级**变换：把目标部件的 `translate3d(自己位置)` 换成 `scale3d(f)`。部件几何本来就绕自身原点建，丢掉 translate 就等于「中心飞到世界原点」——其余部件原地不动 |
| **`pointerdown` 里 `preventDefault()`** | 取消 pointerdown 会让浏览器**连带抑制掉兼容鼠标事件**（含 `click`）。「点部件放大」整条路径失效，不报任何错 | 别拦；拖动不想选中文字就用 CSS `user-select:none` |
| **`setPointerCapture` 重定向 `click`** | 捕获之后 pointerup 被重定向到台面，于是 `click.target` 也变成台面——认不出点的是哪张面片 | pointerdown 时把 `e.target` 记下来，click 里用它（而不是 `e.target`） |
| **台面没裁剪** | 放大后世界溢出到台面外。`.m3d-stage` 是**定位元素**（`perspective` 还让它建了层叠上下文），绘制层级高于后面未定位的 `.m3d-lg`，整块盖住图例把点击吃掉 | 给 `.m3d-stage` 加 `overflow:hidden`。既解决挡点击，溢出的部分也不会糊到图例上，顺带成了「镜头取景」的观感 |

配套的测试也要当心：**`elementsFromPoint` 对 3D 变换的元素按包围盒判定，真实命中按变换后的四边形判定**，
两者对斜着的面片并不一致（扫描说「这里是 m3d-f」，真按下去 `pointerdown` 的目标却是 `m3d-world`）；
`getBoundingClientRect` 的中心也会落到面片外面。挑点击点只能用**真实命中测试**（`elementFromPoint`）扫网格。
另外校验脚本里必须记得关掉平滑滚动（`html{scroll-behavior:auto!important}`），
否则 `scrollIntoView` 之后量到的坐标已经过期，会得到「点了没反应」的假失败。

### 3D 演示路线图：模型自己走一遍装配过程

「点一下放大」回答的是「这个部件是什么」，这一层回答的是另一个问题：
**它是怎么由这些零件凑出来的**——先有哪一段、后有哪一段。做法是让模型本身当演示装置：

- 每个模型在 `modelrigs.py` 里带一份 `road`：4–6 步，每步一个标题、一句话、
  以及**这一步新增哪些部件分组**；
- 点某一步，模型只显示到那一步为止（`applyStep` 给还没装上的部件加 `.off`），
  新增的那一批淡入一次；「全貌」回到完整模型，「自动演示」自己走一遍；
- 下面再排一条**各步快照**：同一批面片、同样的角度，一眼看出每步差在哪，拖动任意一张全部一起转。

#### 分组：靠 `mark()`，不靠给每个图元加参数

几何方法有十来个，逐个传 tag 要改十几处调用点，**漏一个就少一个部件，而渲染上完全看不出来**——
只有路线图会悄悄缺一块。所以在 scene 里按建造顺序插几行 `g.mark('箭体骨架')` 就行：
`mark()` 只记「到第几个部件为止」的边界，`_part_groups()` 再把它摊成每个部件的分组名，
渲染时写成 `.m3d-p` 上的 `data-g`，运行期只做查表。

三条断言（`M3D.road_problems` + `build.model_check_road`）：

| 断言 | 拦住什么 |
|---|---|
| 每步新增的分组加起来 **正好等于** 模型的全部分组 | 少了 → 那部分零件在任何一步都不出现，最后一步也不是完整模型；多了 → 同一个分组被两步认领，「新增了什么」说不清 |
| 每步的 `g` 都必须是这个模型真实存在的分组名 | 名字打错、复制粘贴时漏改 |
| **反解渲染出来的 HTML**：部件上的 `data-g` 集合 == 里程碑按钮认领的集合 | `_part_groups()` 错一格、或者渲染路径把 `data-g` 丢了——这类错不会让页面报错，只会让演示悄悄不对 |

#### 两个必须记住的实现细节

| 细节 | 为什么 |
|---|---|
| 隐藏部件**只压面片的不透明度**，`.m3d-p` 上只挂 `visibility` | `opacity` 是 grouping property，挂在 `.m3d-p` 上会给它建层叠上下文、把 `preserve-3d` 子树**压平**，整个部件塌成一团（和「点一下放大」压暗时踩的是同一个坑）。`visibility` 正常继承、不建层叠上下文，3D 位置照旧。隐藏要**延迟**到淡出结束（`transition:visibility 0s .32s`），显示则必须立刻（延迟 0s），否则会有半秒空白 |
| 快照**不自带面片**，运行期从主模型的 world 克隆 | 5 张快照各渲染一份会让这一页多出四五倍 HTML；而两者本来就必须长得一模一样，克隆天然一致。克隆时 `transform` 取 `focus[j].base`（**不能抄 `el.style.transform`**——主模型可能正停在「放大某个部件」的状态上）；整条默认 `hidden`，靠包裹 `.m3d` 的 IntersectionObserver 懒建，打印前 `beforeprint` 补建 |

#### 四个坑

| 坑 | 症状 | 正解 |
|---|---|---|
| **快照骨架里留了个占位的 `.m3d-world`** | 克隆是 `appendChild`，那个空壳留在最前面，`mini.querySelector('.m3d-world')` 永远拿到空壳——「快照跟着主模型转」整条静默失效（`--ry` 写在第二个 world 上），画面上完全看不出来 | 骨架只给空台面，world 一律由克隆产生。**这条是校验脚本抓出来的**，肉眼一点都看不出来 |
| **`.m3d-strip` 少了 `min-width:0`** | `.m3d` 是网格容器，网格项的自动最小尺寸是「内容最小宽度」，而快照条 5 个 `minmax(150px,…)` 轨道的内容最小宽度接近 790px。于是窄屏下路线图与快照条一起被撑到 790px，里程碑卡被父级裁掉半截 | 给 `.m3d-road / .m3d-strip` 加 `min-width:0`，横向滚动交给 `.m3d-snaps` 自己的 `overflow-x`。**注意这个错量不出整页横向滚动**（页面外层有裁剪，`documentElement.scrollWidth` 仍是视口宽），断言只能直接比「路线图宽度 − 容器宽度」 |
| **里程碑条用 `auto-fit` 网格** | 列数由容器宽度除最小列宽决定，5 步被断成 4+1，最后一块孤零零占一行 | 改 flex：`li{flex:1 1 120px}`，一行能塞几个塞几个、并等分剩余宽度，4~6 步都是一行排满 |
| **文字没过 `rich()`** | `models3d.py` 直接拼 HTML，不经过 `build.py` 的 `rich()`——页面上把 `**强调**` 连同星号原样显示了出来 | 在 `build.render_model` 里先用 `road_text()` 转一遍，`models3d.py` 仍旧只认纯文本 |

#### 一个只会在纸上暴露的坑：卡片不能被切成两页

模型 + 路线图 + 快照合成**一张**卡片时，实测 1773px，而 A4 一页的内容区只有 1017px。
打印样式里本来就有 `figure{break-inside:avoid}`，但**浏览器对「高过一页的块」会直接忽略这条规则**——
于是卡片底与边框被页边切开，`check_print.py` 报 2 处「图形被页边切断」。

正解是拆成**两张卡片**：模型一张、路线图 + 快照一张，外面套一个 `[data-m3d]` 作为同一个「交互范围」
（拖动、点步、快照克隆都还当作一个模型）。两张各约 610px / 500px，都装得下一页，规则这才真正生效。
顺带把路线图那张的打印版排成一行五个快照——纸上是固定的 A4 宽，排成一行才是「一条时间轴」该有的样子；
排成两列三行会让这张卡片长到 976px，逼近 1017px，太冒险。

#### 校验：为什么必须在这一侧量

- `check_site.js` **不滚到模型**，快照条还停在 `hidden`，量不到它的宽度；
  而量整页横向滚动也没用——页面外层有裁剪，`.m3d-road` 涨到 790px 时
  `documentElement.scrollWidth` 依旧等于视口宽（实测过）。
  所以这条断言放在 `check_visual.js` 的路线图段里，**建完之后直接比「路线图宽度 − 容器宽度」**。
- 交叉验证：点第 k 步之后主模型上**可见的部件数**，必须正好等于第 k 张快照里**克隆下来的部件数**。
  一边是运行期按 `data-g` 过滤 `.off`，一边是构建期按同一步切出来的面片集合——两条独立路径。
- 负向测试共十一组，每组都确认过自检会红：分组少认领 / 重复认领 / 认领不存在的名字 /
  某步没写说明 / `mark()` 重名 / 渲染文本里的分组对不上 / 快照张数比步数少 /
  视角不广播 / 不隐藏部件 / 不禁用图例 / 去掉 `min-width:0`。

### 虚拟视图

十张，每张一个仪表框 + 一个运行场景 + 四个读数。**眉标里那句「模拟 · 非实拍」不能省**：
这一层画的是运行状态，很容易被当成实拍图或实测数据；站点里所有数字都有出处，
唯独这类图是按公开参数推的，必须写在脸上。

## 视觉设计：舷窗（viewport）+ 仪器面板

设计语言是**两套底色分工**，这条分工是整套视觉的地基，改样式前先认清它：

| | 用途 | 底色 | 文字色 |
|---|---|---|---|
| 浅色面 | 正文、表格、长文、图注、打印 | `--page` / `--bg` | `--text` / `--muted` |
| 　└ 下沉面 | 卡片**里面**的块（图框、参数表、提示行） | `--bg-sunk` | `--text-soft` / `--muted` |
| 深色「舷窗」 | 只给**关键面**：首屏、KPI 仪表条、收口卡片、图框顶线与四角 | `--void*` | `--void-text` / `--void-soft` / `--void-muted` |

**四条不能往回改的约定**（都踩过一次，改错就会丢掉整体感）：

1. **浅色面是冷中性，不是暖中性。** `--page:#edf1f5` 这一族和深色面**同色温**。
   最早用的是暖中性（`#f5f5f2`）+ 近黑深色，结果读起来像「白纸上贴了一块黑」——
   两套色温打架，页面是拼起来的而不是一体的。**改配色时不要单独把一边改回暖色。**
2. **深色面是石板蓝灰，不是近黑。** `--void:#2b3a4b`。近黑会把对比推到刺眼、
   让深色面「浮」在页面上；石板色才有「沉进去」的感觉。
3. **首屏与 KPI 是一整块控制台。** 靠 `.hero:has(+ .kpis)` 去掉相邻边的圆角与间距。
   它们原本是两块各自带圆角的深色面板、中间还有 18px 缝，读起来像「贴了两次深色」。
4. **页面顶部有一抹极淡的石板渐变**（`body` 的 `background-image`，340px 内淡出）。
   就是这一点让控制台是「沉进页面」而不是「压在页面上」。它很不起眼，但去掉之后
   控制台下沿会立刻变成一条生硬的分界线。
5. **最小号的文字不用最浅一档灰。** `--faint`（`#97a0ae`）在浅底上只有 **2.33:1**，
   达不到 WCAG AA——它只留给装饰性笔画（HUD 转角之类）。凡是**承载信息的 10–11.5px 小标签**
   （图注、`h2 .en`、层序号块、侧栏分组标签、图例标题）一律走 `--muted`。
   这一条是被校验逼出来的：新加的侧栏分组标签用了 `--faint`，`check_visual.js` 立刻报 2.33:1。

⚠️ **不要在深色底上复用浅色面的文字色**（`--text` / `--muted` / `--faint`）——
它们在深底上的对比度不够。深色面有自己的一套 `--void-*`，其中 `--void-faint` 比浅色面的
`--faint` **更亮**，就是为了保证最小号文字也读得出来。`tools/check_visual.js` 会按 WCAG AA
逐个核关键文字的对比度，改完颜色一定要跑一遍——屏幕上看「还行」和真的达标是两回事。
（当前实测最低 5.76:1，阈值 4.5。）

**浅色面自己分三档**：页面底 `--page` → 卡片白 `--bg` → 卡内下沉面 `--bg-sunk`。
`--bg-sunk` 原来只比白低一点点，「卡中卡」（图框嵌在步骤卡里）看不出边界；
压深一档到 `#f0f5fa` 之后嵌套关系才读得出来。**但压低它会连带压低上面所有小字的对比度**——
这次就是它把 11px 图注压到了 4.48:1，最后靠把 `--muted` 从 `#69717f` 提到 `#636c7a` 补回来。
**动这两个值必须成对跑视觉校验。**

### 舷窗背景是生成出来的，不是手画的

`tools/spaceart.py` 用**固定种子的 LCG**（不用 `random`）生成 `assets/space.svg` 与
`assets/space-tile.svg`：星场、坐标网格、轨道弧、一艘极简星舰剪影 + 它的虚线轨迹。

两条约束：

1. **必须确定性。** 星位每次构建都要一模一样，否则「构建产物可复现、按字节比对校验」
   这条流水线直接失效。
2. **输出成独立文件，由 CSS 的 `background-image` 引用，不要内联。**
   CSS 里的 `url(space.svg)` 相对 site.css 解析，所以首页与板块页拿到的是同一个文件；
   内联的话 11 个页面各背一份十几 KB 的星场，白涨 150KB。

星场里有一块**文字安全区**（`safe=` 参数）：落在标题区域的星被压暗到 0.26 不透明度，
保证深底上的文字不被亮点干扰。

### 动效只有三种，都挂在 `prefers-reduced-motion` 上

1. **进场**：`site.js` 给 `.hero / .kpis / .figure / .note / section > h2,h3` 加 `.reveal` 类，
   IntersectionObserver 进视口后加 `.in`。**类名由 JS 加**，所以脚本没跑起来时页面照常全可见；
   另有 4 秒兜底定时器与 `beforeprint` 兜底，防止 IO 不触发把内容永久藏起来。
2. **星场极慢漂移**：120 秒一个来回，只动背景层，不动内容。
3. **悬停反馈**：卡片顶线、表格行信号色浸染、导航胶囊。

系统开了「减少动态效果」时，三者全部跳过（JS 直接 return，CSS 的 `@media` 也不生效）。

### 深色面在打印时必须还原

`@media print` 里把所有深色面板改回白底黑字、隐藏星场与 HUD 转角、关掉全部动画。
这份报告的用途之一就是打印，**任何新增的深色面都要同步补一条打印还原规则**。

## 板块配色：每个板块都不一样，但仍是一套东西

站点现在有**三条颜色轴**。加任何新颜色之前，先认清它们各回答什么问题——
混在一起就会互相打架：

| 维度 | 回答 | 变量 | 用在哪 |
|---|---|---|---|
| 状态色 | 这件事**到哪一步**了 | `--green/--blue/--amber/--red/--gray` | 小标签（已实现 / 在验证 / 待突破 / 物理约束 / 仅纸上） |
| 位置色 | 这是**第几层** | `--ly1..--ly5` | 层序号块、层分隔线的短段、侧栏层项的小方块 |
| **板块色** | 这是**哪个板块** | `--bd-ink / --bd-deep / --bd-wash / --bd-glow` | 页面顶部渐变、深色舷窗的底与星云、眉标、进度条、首页卡片编号 |

**一条铁律：板块色绝不进小标签。** 一枚绿色小标签必须永远是「已实现」的意思，
不能因为换了个板块就变成「火箭技术」。所以板块色只铺在「环境」上，不进语义标记。

### 十个色相是按主题挑的，不是等距分的

| 板块 | 色相 | 为什么 |
|---|---|---|
| 01 目前航天 | 钢铁蓝 208° | 行业基线，也是全站默认色 |
| 02 火箭技术 | 焰橙 14° | 发动机热流与试车台 |
| 03 星舰 | 不锈钢青灰 192° | 舰体的冷金属 |
| 04 飞船生态圈 | 苔绿 146° | 生保系统与植物 |
| 05 光速推进 | 深天蓝 228° | 光束与深空 |
| 06 寿命与冬眠 | 靛紫 258° | 低温与沉睡 |
| 07 外星交流 | 罗兰紫 284° | 射电与远方 |
| 08 宇宙资源 | 赭金 34° | 小行星金属矿 |
| 09 AI 与机器人 | 青碧 170° | 传感与算力 |
| 10 星船总体设计 | 石墨蓝灰 216° | 综合页，**刻意最灰**——它不描述某个领域 |

### 每一档色都是「按亮度反解」出来的，不是写死明度

`tools/boardskin.py` 对每个板块算出四档 + 一条五级栏目色阶，全部落在同一条亮度线上：
ink（浅底文字，5.6:1）、deep（深色舷窗底，与 `--void` 同亮度）、wash（页面顶部渐变）、
glow（深底上的亮色，6.2:1）、`--ly1..5`（≥5.3:1）。

⚠️ **不能用 HSL 明度当感知亮度。** 第一版写死明度 0.315，结果苔绿只有 4.55:1、
蓝色却有 6:1——亮度公式里绿占 0.715、蓝只占 0.07，色相一变亮度差很多。
现在用二分法对每个色相反解出「亮度等于目标值」的明度，十档才站在同一条线上。

对比度**在构建期就断言**（`build.py` 会跑 `boardskin.check()`），不达标直接构建失败——
十板块 × 四档色 × 两种底色，靠人眼核不过来。

### 每个板块一张专属星场

`tools/spaceart.py` 按板块生成 `assets/space-<slug>.svg`（舷窗大图）与
`space-tile-<slug>.svg`（KPI 仪表条的小瓦片），共 22 张。差异来自三处：

1. **星云辉光**用板块亮色，**只放在图的右半**；
2. **星位种子由 slug 派生**（`zlib.crc32`，**不能用内置 `hash()`** —— 它每个进程都变，
   会让「构建可复现 + 按字节校验」失效）；
3. 轨道弧、轨迹与星舰的偏移量也由种子派生。

**文字安全区**（图左侧 68%）里星点压到 0.18 以下、**并且不画十字光芒**——
光芒是白色、可以亮到 0.95，一个 32×32 小块里落一颗就能把底色对比度从 6:1 拉到 3.9:1。
只压暗星点、不砍光芒的话，数字几乎不动（试过）。

### 四个把这件事做错的地方（都踩过）

1. **per-page 的 `<style>` 必须放在样式表之后。** 两者都是 `:root`，同优先级下后写的赢；
   放在前面会被 site.css 的默认值覆盖——症状是「十个板块的首屏长得一模一样」。
2. **媒体查询不增加优先级。** 窄屏的 `background-position` 覆盖必须写在样式表**末尾**，
   否则会被视觉层里 `.hero .sky` 那条 `background` 简写覆盖（症状是「规则改了，数字一点没动」）。
3. **`url()` 写在自定义属性里时，解析基准是样式表而不是文档。** 所以变量里只写文件名
   （`url(space-01.svg)`），写 `assets/` 会变成 `assets/assets/…` 404。
4. **量星场亮度必须按真实的 `background-position` 取景。** 窄屏下 `cover` 只露出图的约 1/3 宽，
   取错区域会量到星云那一侧，得出「窄屏只有 3.95:1」的假结论——实际文字坐的是纯暗底 6.2:1。
   而且 CSS 会把 `left` 算成 `"0% 50%"`，不能按字符串匹配 left/right。
   `check_visual.js` 现在按百分比语义还原取景，并在**桌面与窄屏两个宽度**上各量一次。

## 可访问性、多宽度适配与三条硬规矩

这一节是「看不见但会真的坏」的那一部分。三条规矩都对应一个真实缺陷。

### 规矩一：内联 SVG 的 marker / gradient id 必须每张图唯一

一个板块页会内联二十多张 SVG。图元库原先每张图都写 `<marker id="da">`（`iso.py` 是 `ar`），
**一页 18–19 个重名 id**：

- HTML 非法（id 必须全页唯一）；
- `url(#da)` **只命中文档里第一个** marker。因为所有箭头长得一样，视觉上看不出问题——
  但哪天某个图换了箭头样式，全页箭头会一起变成那一个。

做法是在 `svg()` 里按实例生成后缀（`f'da{next(_SEQ)}'`），输出前把 `url(#da)` 一并改写。
**别改调用点**（有十几处），在生成端一次性解决。
`check_site.js` 现在会断言「全页无重复 id」。

### 规矩二：负 margin 出血会撑宽文档，`overflow:clip` 救不了

顶部胶囊导航原本用 `margin:0 -22px; padding:0 22px` 让胶囊条出血到屏幕边缘。
结果 **≤1080px 的每个宽度都横向溢出**（手机 +16px、平板 +22px）——手机上整页能左右拖动。

踩坑点：先试了 `overflow-x:clip`，**没用**。clip 只裁子元素，**不改元素自身的盒子宽度**，
而负 margin 撑宽的正是 nav 自己。
正确做法是让内边距进入滚动内容：`.topnav{margin:0}` + `.topnav .inner{padding:0 22px}`，
滚到最左时首项仍有内缩，向右滚时胶囊照样滑到边缘之下，而 nav 恰好等于视口宽。

### 规矩三：横向溢出要跨宽度带测，而且不能拿 `innerWidth` 当基准

上面那个溢出 **藏了很久**，因为校验只测了 1366 与 390 两个宽度，
而断点恰好落在 641–1080（侧栏隐藏、胶囊导航出现）这一段。

更隐蔽的是**断言本身失效**：原来写的是
`scrollWidth > window.innerWidth + 1`，而 `isMobile` 模拟下 `innerWidth` 会被撑成内容宽
（= `scrollWidth`），于是「有横向溢出」永远判成 false——**看着是绿的，其实一直在漏**。

现在两处都改了：基准换成 `documentElement.clientWidth`，并加了一段跨宽度扫描
（700 / 900 / 1024 三个宽度，对带表格的板块页与首页各跑一遍）。

### 键盘与读屏

- **跳转链接**：`<a class="skip" href="#main">跳到正文</a>`，平时 `transform` 移出视口，
  获得焦点时浮出。键盘用户不必 Tab 过十几个导航项才能到正文。
- **焦点环**用 `:focus-visible`（不是 `:focus`）——鼠标点击不该看到焦点环，键盘操作必须有；
  用信号青色，和整体色语言一致。
- **`aria-current="page"`** 标在当前板块上（侧栏与顶部导航各一处，所以板块页是 2 处、首页 0 处）。
- **`theme-color`** 必须跟着页面底色走。它原来是暖中性时代的 `#f5f5f2`，
  改冷色之后一直没跟着改——手机浏览器地址栏会显示一个和页面不搭的暖灰。

## 打印与 PDF：分页是在导出那一刻才决定的

这份报告的用途之一是打印。**分页问题在浏览器里永远看不见**——截图、DOM 断言、
对比度检查都管不到「哪一行落在页底」，所以必须真的导一份 PDF 来量。

```bash
# ① 导出（需要本机 playwright）
NODE_PATH=<node-workspace>/node_modules node tools/make_pdf.js \
  http://127.0.0.1:4321/sections/02-rocket-tech.html /tmp/p2.pdf

# ② 检查（需要 pymupdf：pip install pymupdf）
python3 tools/check_print.py /tmp/p2.pdf
```

`check_print.py` 报四个指标：页数、**填充率中位数**、低于 75% 的页数、
近乎空白的页；外加两个缺陷判据（被页边切断的图形、页底残留的空盒子）。实测结果：

| 页面 | 页数 | 填充率中位数 | 近乎空白页 |
|---|---|---|---|
| 首页 | 3 | 93% | 0 |
| 板块二 | 25 | 94% | 0 |
| 板块九 | 26 | 96% | 0 |
| 板块十 | 11 | 91% | 0 |

### 分页规则分三层（改动前只有一条，而且是无效的）

原来的打印样式里只有 `section{page-break-inside:avoid}`。**一个栏目节高 2,000–5,000px，
远超一页，浏览器对「高过一页的元素」只能忽略这条规则**——等于没写。现在按尺寸分三层：

1. **标题绝不留在页底**：`h1,h2,h3,.grp-hd{break-after:avoid}`。
2. **矮的原子块整块搬走**：图、提示块、首页卡片（约 330px）、`trbook`、`chain-bar` 等
   ——`figure,.note,.frontier,.trbook,.chain-bar,.cb,.vt-i,.entry,.trb,.board-card,.kpi`。
3. **表格允许跨页，但行不切开、表头每页重复**：`tr{break-inside:avoid}` +
   `thead{display:table-header-group}`。

### 三条实测出来的取舍（都量过，别凭感觉改）

- **不要给高大的步骤卡加 `break-inside:avoid`。** `.trs > li` / `.vs > li` 单个 600–800px，
  加上之后填充率中位数从 96% 掉到 77%、总页数 +3——为了让「卡片边框不被切」而空掉三分之一页，
  不划算。让它们拆开，但内部的图和表仍然不被切。
- **表格不要整表保护。** 板块十那张 588pt 高的基准配置表装不进上一页剩余空间，
  整块搬走会让上一页只剩 153 字（11 页里出现 1 页近乎空白）。改成「允许拆分 + 表头重复」后，
  板块十空白页归零、板块二还少了一页（26 → 25）。
- **首页卡片值得保护。** 不保护时卡片被页边切开，上一页只剩一个空框的圆角顶边；
  加上之后页数不变（3 页），是白赚的。

### ⚠️ 一个差点误判的坑

`break-inside:avoid` 把盒子搬到下一页时，**盒子的边框可能被画在上一页的页边距区域**。
这种「幽灵边框」在纸上不可见（放大看是纯白），但会被朴素的检测判成「图形被切断」。
`check_print.py` 因此排除了「起点已经落在内容区之下」的图形。

### 表格的表头语义

`build.py` 的 `tag_th_scope()` 会给**所有**表头补 `scope="col"`。表格来自四处
（生成器 3 张 + `board01_body.html` + `content_c.py`），逐个改容易漏，所以在渲染最后统一补一次。
模式必须卡住 `<th` 后面是空白或 `>`——否则会误伤 `<thead>`。

## 技术说明

- 纯静态：无运行时依赖、无 CDN 引用，图表为手写内联 SVG
- 桌面端：左侧粘性目录（板块 + 当前板块小节）+ 滚动高亮 + 顶部阅读进度条
- 移动端（<640px）：侧栏隐藏、顶部切换为横向胶囊导航、表格自动转为卡片式（`td::before` 带字段名）
- 每个板块页底部有上一/下一板块导航
- 部署：推送 `main` 由 GitHub Actions 发布到 GitHub Pages。
  ⚠️ **每个提交都会触发一次部署，而工作流的并发组 `pages` 只保留最后一个**——
  所以批量推送（一次一个文件、十几个提交）时，前面的部署会显示为 `cancelled`，
  这是正常的，不是失败，**等最后一个跑完即可**。
  另外 `deploy` 步骤偶尔会瞬时失败（`build` 成功但 `deploy` 失败），
  这时再推一次任意提交重新触发即可，**不必改内容，也不必连推多次**——
  连推只会产生更多被取消的 run，把队列堵得更久。
  ⚠️ 更要注意的是：**短时间内大量提交会触发 GitHub 的部署二级速率限制**，
  表现为 `build` 一直是绿的、`deploy` 连续几次都红（且日志要 admin 权限才看得到，匿名拿不到）。
  这种情况**只能等**（数十分钟），期间**不要反复重推**——每次重试都在加重限流。
  所以批量改动应当**合并成少数几次提交**再推，别一个文件一个 commit。
